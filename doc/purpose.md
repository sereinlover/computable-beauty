# Project Purpose — Computable Beauty

> 理解项目背景与目标时参考此文件。影响技术优先级和功能取舍的判断依据在这里。

---

## 核心命题

**音乐的"美"是否可以被计算？**

这不是一个修辞问题，而是整个系统的设计驱动力。Yoshiki 的音乐能同时装下四层：精确的节奏结构（物理层）、古典与摇滚的对位逻辑（结构层）、对死亡与失去的直面（生命层）、无法解释的情绪击穿感（情感层）。这个项目试图把这种直觉翻译成可计算的维度。

---

## 开发者背景

- 8 年后端工程师，主语言 Golang + Python
- 当前处于 GAP 阶段，从后端转向 MIR 算法工程

**与技术决策的关联**：Python engine 层需要更多 MIR/ML 相关说明。

---

## 目标岗位：MIR 算法工程师

项目需要覆盖的 JD 核心能力：

| JD 要求 | 项目中的对应模块 |
|---------|----------------|
| 流派/情绪/乐器分类 | L2 理解层（GenreClassifier、EmotionClassifier、InstrumentClassifier） |
| 音频特征提取 | L1 特征层（librosa pipeline） |
| 数据集建设与治理 | `dataset-curator` Skill |
| 模型落地与推理加速 | ONNX 导出 → Golang Runtime（Stage 6） |
| 工程能力 | 三服务架构、SKILL 注册表、Harness 编排 |
| 美学评价 | L3 评估层（四维美学指数，本项目的差异化核心） |

**核心展示点**：L2 分类器和 L3 美学评分是项目最核心的展示点，必须做实。

## 开发阶段概览

| 阶段 | 内容 | 核心交付 |
|------|------|---------|
| Stage 0 | 合约定义与骨架搭建 | 三服务跑通，Mock 数据，真实 Claude 解读 |
| Stage 1 | L1 特征层 + 数据集治理 | 真实 librosa pipeline，训练数据就绪 |
| Stage 2 | L2 基础分类 | 流派 / 情感 / 乐器分类器 baseline |
| Stage 3 | L2 进阶 MIR | 结构分段、和弦识别 |
| Stage 4 | L3 美学评分 | 四维指数计算与标定 |
| Stage 5 | L4 Harness | Mock → 真实工具调用，证据链 |
| Stage 6 | 优化 + 部署 | ONNX 导出，Redis 缓存，Fly.io |
| Stage 7 | 写文章 | 技术叙述，面向外部发布 |

阶段不严格串行：每完成一个 Skill 就接进 Agent 验证，Stage 0 骨架贯穿全程。

## 产品受众

**直接受众**：面试官（MIR / 音乐 AI 方向）

**产品层面的真实受众**：
- 对特定音乐有强烈情感依附、想"理解"它的发烧友、独立音乐人、乐评人
- 更有商业价值的是平台层：推荐系统（需要比流派标签更细腻的信号）、音乐教育、音乐治疗、影视授权

**对开发决策的含义**：当前产品形态（单曲 Web 界面）是概念证明，不追求规模，优先展示系统完整性和可解释性。
